# Argus 压测报告（精简版）

> 被测：`POST /api/v1/error`（单条）+ `POST /api/v1/error/batch`（批量，≤50 条）
> 环境：api `cpus=2`、worker `cpus=1`、`RATE_LIMIT_ENABLED=false`、`LOG_LEVEL=warn`、schema `bench`
> 机器：Intel i5-8300H（4 核 8 线程）/ 7.9 GB 内存 / Docker VM 见 4 GB
> **压测机与被测服务同机**（SRS R-02 已知限制，绝对值偏保守）
> 每配置：预热 3 s（丢弃）+ 3 轮 × 30 s，**取中位数**；每组前清表 + 清队列 + 等 3 s

---

## 0. 摘要

| 项 | 结论 |
| --- | --- |
| 单条模式天花板 | **296 ~ 330 events/s** |
| 批量模式天花板 | **1,024 events/s**（batch=50，接入层） |
| 消费速率 | 逐条 **63 events/s** → 批量化后 **688 events/s（10.9×）** |
| 最终系统状态 | 接入 **869** / 消费 **688** events/s，队列积压归零，两端基本同步 |
| **头号瓶颈** | **JS 主线程**（线程级实测 96.2%，每请求约 3.08 ms → 理论上限 325 req/s，与实测吻合到 2%） |
| 已证伪 | ~~2 核 CPU 配额限制吞吐~~（4 核后吞吐无提升、节流归零） |
| 已排除 | PG 连接池（active ≤12 « 17）、磁盘 IO（等待 0~1）、fsync（WALWrite 累计 8） |

**一句话**：单条模式下天花板由 **JS 主线程每请求约 3 ms** 决定，加核无用；批量把每请求成本摊薄 50 倍后接入抬到 1,024 events/s，瓶颈随即转移到消费端；消费端批量化把归并速率提到 688 events/s，**流水线积压从 8 万条降到 1,400 条**。

## 1. 瓶颈演进时间线（本报告的主线）

| # | 阶段 | 观测 | 结论 | 动作 |
| --- | --- | --- | --- | --- |
| ① | 单条基线 | 并发 1→10 涨 3.2 倍，10→50 持平，50→200 反降 | 存在硬天花板 | — |
| ② | 探针归因 | CPU 171%、`nr_throttled` 25 s 内 +41、PG 行锁最多 8 个并发 | 疑为配额受限 + 行锁竞争 | 消行锁 |
| ③ | A/B 消行锁 | `session_id`/`user_id` 唯一化：**291.7 → 331.1 events/s（+13.5%）** | 行锁确实吃吞吐 | 已修复 |
| ④ | 四核对照 | 4 核：300.9 / 309.5 / 323.4，**节流 0%，CPU 仅 1.8/4 核** | **配额不是原因** | 推翻② |
| ⑤ | 线程级定位 | 主线程 **96.2%**，其余 15 线程合计 86% | **主线程饱和** | 定案 |
| ⑥ | 批量上报 | batch 1→10→50：**296 → 539~837 → 1,024 events/s** | 主线程模型成立 | 已实现 |

> 进程 171% 可以是"主线程 100% + 辅助线程 71%"。**判断是否单核饱和只能看线程级数据。**

## 3. 各实验要点

### 3.1 单条模式：拐点在 10 并发

| 并发 | 1 | 10 | 50 | 200 |
| --- | ---: | ---: | ---: | ---: |
| events/s | 117 | **372** | 356 | 339 |
| 单连接效率 | 116.8 | 37.2 | 7.1 | 1.7 |
| p50 (ms) | 7 | 24 | 125 | 531 |

吞吐在 10 并发到顶，之后加并发只增延迟 —— 典型的**服务端饱和**，不是压测端问题。
12 轮里出现过两处单轮塌方（50 并发一轮 241 rps、200 并发一轮 p97.5 炸到 9.4 s），
这正是"必须 3 轮取中位数"的现场证据。

### 3.2 行锁代价：唯一化身份字段 → +13.5%

压测 payload 原先把 `session_id`/`user_id` 写死，导致 50 并发反复 UPSERT `sessions` 的同一行。
改成每事件唯一后（同并发、同环境、只改这一处）：

| 指标 | 旧口径 | 新口径 | 变化 |
| --- | ---: | ---: | ---: |
| events/s | 291.7 | 331.1 | **+13.5%** |
| p50 / p99 | 161 / 292 ms | 142 / 241 ms | −11.8% / −17.5% |
| max | 1,469 ms | 756 ms | −48.5% |

**结论稳健**：新口径最差一轮（322.1）仍高于旧口径最好一轮（304.9，+5.6%），不依赖中位数运气。
代价主要体现在尾部 —— 行锁不会均匀分摊，而是偶发地把单个请求拖长。

### 3.3 四核对照：加核无用（推翻了"配额受限"）

| | 2 核 | 4 核 |
| --- | ---: | ---: |
| 中位 events/s | 331.1 | 300.9 / 309.5 / 323.4 |
| 平均 CPU | 171% | 161~182%（上限 400%） |
| `nr_throttled` | 持续上涨 | **0%** |

**加核后吞吐没有任何提升，节流完全消失，CPU 只用了 1.8/4 核。**

线程级采样（`/proc/1/task/*/schedstat`）：

| 线程 | CPU |
| --- | ---: |
| **tid 1（JS 主线程）** | **96.2%** |
| 4 个辅助线程 | 各 ~16% |
| 3 个 V8 GC/编译线程 | 各 ~5% |
| 合计 | 182% |

**定量闭环**：`96.2% ÷ 312.5 rps ≈ 3.08 ms/请求` → 理论上限 `1 s ÷ 3.08 ms ≈ 325 req/s`，
与实测 331 吻合到 2%。**天花板完全由主线程成本决定。**

2 核配额仍有影响，但**只影响尾部**（突发超配额被暂停），不影响上限。

### 3.4 批量上报：接入层 3.46 倍

| | batch 1 | batch 10 | batch 50 |
| --- | ---: | ---: | ---: |
| req/s | 296.0 | 53.9~83.7 | 20.5 |
| **events/s** | 296 | **539~837** | **1,024** |
| 单事件延迟 | 156 ms | 55~56 ms | **46 ms** |

**批量不是"用延迟换吞吐"**：单事件延迟反而从 156 ms 降到 46 ms，两头都赢。

⚠️ **batch=10 不稳定**：两次独立运行 539 vs 837（+55%），其中一次出现 36 次超时。
报告里写"539~837"区间而非单值。batch 两端（1 和 50）三轮内部都很紧，中间反而抖。

⚠️ **效率只拿到 3.46%**：若主线程成本完全线性摊薄，batch=50 应为 `296 × 50 ≈ 14,800`，
实测 1,024 —— 说明每请求仍有大量无法摊薄的固定开销。

### 3.5 消费端批量化：worker 10.9 倍

改造前每处理一条事件要写 4~5 条 SQL，其中**两条打在同一行 `error_groups`**（`times_seen +1`、
`users_seen +1`）。改成"一个 job 带 N 个主键，`times_seen` 一次 `+= N`"后：

| 指标 | 逐条消费 | 批量消费 | 变化 |
| --- | ---: | ---: | ---: |
| worker 消费速率 | ≈63 events/s | **≈688 events/s** | **10.9×** |
| 结束时未归并事件 | 86,050（几乎全部） | **1,400** | −98% |
| 结束时队列积压 | 80,869 | **0** | 清空 |
| 接入 events/s | 1,024 | 869 | −15% |
| p50 / p99 | 2,301 / 4,271 ms | 2,368 / 4,406 ms | +3% |

**接入略降 15% 的合理解释**：worker 现在做了 10 倍以上的数据库写入，与 API 抢同一套 PG/CPU ——
"总系统吞吐上升、API 份额下降"的正常现象。且在轮次波动范围内（旧数据三轮本身有 2 倍抖动），
不宜过度解读。

**结果**：系统从"接入受限 + 消费严重滞后（小时级积压）"变成"接入 869 / 消费 688，基本同步"。

## 4. 当前状态与下一步

### 4.1 已排除的怀疑方向（不要再查）

| 已排除 | 依据 |
| --- | --- |
| JS 主线程 | 96.2% 打满，定案 |
| 2 核 CPU 配额（作为吞吐上限） | 4 核实测无提升、节流归零 |
| PG 连接池 | active ≤12 « 上限 17 |
| 磁盘 IO / fsync | IO 等待 0~1，WALWrite 累计 8 |
| 单行 `sessions` 行锁 | 唯一化后 +13.5%，已修复 |
| worker 消费速率 | 63 → 688 events/s，已修复 |

### 4.2 下一步（按优先级）

| # | 动作 | 目的 |
| --- | --- | --- |
| 1 | 补"单条失败降级" | 现在**批内一条出错 = 整批 50 条回滚重试 + 进 DLQ**，逐条消费时只影响那一条 |
| 2 | `node --cpu-prof` 拆 API 侧 46~52 ms/条 | 接入 869 与消费 688 已接近，找下一层天花板；也能解释"效率只有 3.46%" |
| 3 | 观察 `idle in transaction` 时长 | 批量事务变长会持锁更久，必要时把 `error_groups` 的写挪到事务最后一句 |
| 4 | 用多指纹 payload 复测 worker | 验证"63/688 这个数是否被 bench 的单一指纹放大了" |

> ⚠️ **不要做**：加大 batch、给 API 加 CPU 核 —— 两者都已实测对端到端吞吐无效。

## 5. 方法论（比数字更值钱）

1. **每次压测前必须同时清表 + 清队列 + 等 3 秒**。只清表会把垃圾 job 留到下一轮，
   同一配置能差出 15%（253 vs 292 events/s）并出现单轮塌方。
2. **多轮压测之间要重启容器**。一次实测出现 43~70 次超时、吞吐掉到 299，
   但采样显示 PG 34%、api 39%、锁等待 0 —— 重启后同样命令跑出 869、零超时。
   根因是上一轮的超时请求还堵在进程里，**不是代码缺陷**。
3. **3 轮取中位数**。单轮里出现过 rps 掉 32%、p97.5 炸到 9.4 s 的离群。
4. **一次只改一个变量**。
5. **跨批次绝对值不可直接比** —— 轮次时长、隔离措施、队列状态任一项不同，绝对值就会漂。
   只有同一批内的同配置对比是受控的。
6. **判断"消费不过来"要看压力停止之后**。刚停时看到 2.2 万条未归并就写"worker 追不上"是错的，
   它在 6 分钟内追平了。正确表述是"持续负载下积压增长，停压后收敛"。
7. **"进程 CPU%"不能用来判断单核饱和**，只能看线程级数据。
8. **单测锁的是行为，不是字符串**。重构后一个测试因"日志里丢了 event_id"而失败 ——
   正确的处理是**修日志**而不是改测试。

## 6. 复现

```powershell
cd E:\Argus\backend
$env:BENCH_KEY='<bench schema 里的项目公钥>'   # 注意与 public schema 的公钥不同

function Reset-Bench {
  docker exec argus-postgres-1 psql -U argus -d argus -q -c "TRUNCATE bench.error_events, bench.error_groups, bench.issue_stats_hourly, bench.sessions, bench.affected_users, bench.performance_metrics CASCADE;"
  docker exec argus-redis-1 sh -c "redis-cli --scan --pattern 'bull:*' | xargs -r redis-cli del"
  Start-Sleep -Seconds 3
}

# 单条基线
Reset-Bench; node scripts/bench.mjs 50 30 3 --out bench/b1.csv

# 批量（新版脚本 --batch=N，同时输出 req/s 与 events/s）
Reset-Bench; node scripts/bench.mjs 50 30 3 --batch=10 --out bench/b10.csv
Reset-Bench; node scripts/bench.mjs 50 30 3 --batch=50 --out bench/b50.csv

# 旧口径对照（session/user 固定，复现 §3.2 的基线）
Reset-Bench; node scripts/bench.mjs 50 30 3 --session=fixed --user=fixed
```

**环境还原**：`docker compose -f docker-compose.yml -f docker-compose.bench.yml up -d --build`

**压完清理**：`docker exec argus-postgres-1 psql -U argus -d argus -c "DROP SCHEMA bench CASCADE;"`

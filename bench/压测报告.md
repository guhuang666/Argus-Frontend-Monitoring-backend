## 0. 摘要

| 项 | 结论 |
| --- | --- |
| 被测系统 | Argus 上报接入 `POST /api/v1/error`（单条事件） |
| 测到的天花板 | **≈ 330 events/s**（api 容器 2 核配额、1.5 KB/条、限流关闭） |
| 拐点 | **50 并发以下**。并发 1→10 提升 3.2 倍，10→50 持平，50→200 反降 |
| 头号瓶颈 | **api 容器的 2 核 CPU 配额**（CPU 中位 171%、`nr_throttled` 持续上涨） |
| 二号瓶颈 | **worker 消费速率**（C2 结束时 29,566 条事件里 22,772 条未归并） |
| 已排除 | 连接池排队（PG active 2~12 « 17）、磁盘 IO（IO 等待 0~1）、fsync（WALWrite 累计 8） |
| 已修正 | 压测 payload 的 `session_id`/`user_id` 写死导致的行锁竞争 → **+13.5% 吞吐** |
| 数据可信度 | 受控对比（A2→B2）可信；跨批次绝对值**不可直接比**（轮次时长、隔离措施不同） |

**一句话**：这不是「代码慢」，是「2 核配额 + 单条上报的固定开销」共同锁死了吞吐；把行锁竞争去掉能拿回 13.5%，剩下的空间要靠加核或批量上报（envelope）才能打开。

## 1. 被测系统与环境

| 项 | 取值 |
| --- | --- |
| 被测接口 | `POST http://localhost:3000/api/v1/error` |
| 请求体 | 旧口径 **1,483 B** / 新口径 **1,535 B**（每 1 条事件） |
| api 容器 | `cpus=2`（`cpu.max = 200000 100000`）、`mem_limit=2g` |
| worker 容器 | `cpus=1`、无内存限制 |
| 其他容器 | postgres / redis / prometheus / grafana **未限** |
| 关键环境 | `RATE_LIMIT_ENABLED=false`、`LOG_LEVEL=warn`、`DATABASE_URL=...?schema=bench` |
| 数据库 | PostgreSQL 16-alpine · schema `bench`（与开发库 `public` 隔离） |
| 压测工具 | autocannon 8 · Node v24.14.1 · keep-alive 复用连接 |
| 压测机 | **与被测服务同机**：Intel i5-8300H（4 核 8 线程）、7.9 GB 内存 |
| Docker VM | NCPU=8、MemTotal ≈ 4 GB（Docker Desktop / WSL2 只分到一半内存） |
| 轮次策略 | 预热 3 s（丢弃）+ 3 轮 × N 秒，**取各列中位数** |

### 环境上的两条硬限制

1. **压测机与被测服务同机**（SRS R-02 已知限制）：autocannon 自己也要吃 CPU，所以这里量到的是「同机情况下的下限」，换到独立压测机应更高。
2. **Docker VM 只有约 4 GB 内存**：宿主机 7.9 GB，但容器世界只看到一半 —— PG 的 shared_buffers 和页缓存都在这个池子里。

## 2. 指标体系

| 字段 | 含义 | 怎么读 |
| --- | --- | --- |
| `conn` | 并发连接数 | 自变量，报告必写 |
| `rps` | 每秒完成（2xx）请求数 | 核心指标；单条模式 = events/s |
| `total` | 单轮完成总数 | 用来验算 `total ÷ duration ≈ rps` |
| `p50_ms` | 中位延迟 | 典型用户体验 |
| `p90` / `p97_5` | 高分位 | autocannon **不提供 p95**，p97.5 是最接近的 |
| `p99_ms` | 99 分位 | 长尾，必须与 `max` 一起看 |
| `max_ms` | 最慢一次 | 分位数抓不到的单点离群 |
| `errors` | 连接级失败 | 不为 0 = 有请求没走通 |
| `timeouts` | 服务端 10 s 未响应 | 不为 0 = 服务端已到崩溃边缘 |
| `non2xx` | 429 / 500 等 | 不为 0 时延迟数据不可信 |
| `MEDIAN(n)` | n 轮中位数 | **报告引用这一行，不引用单轮** |

**派生指标**

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| 单连接效率 | `rps ÷ conn` | 每加一条连接带来多少吞吐；断崖 = 已饱和 |
| Little 理论值 | `conn ÷ (p50 ÷ 1000)` | 稳态理论上限（λ = L ÷ W） |
| 实测/理论 | `rps ÷ Little 理论值` | ≈1 稳态；< 0.6 说明有额外排队未计入 |

**汇总量**

| 指标 | 值 | 判读 |
| --- | --- | --- |
| API CPU | 中位 **171%**，峰值 191% | 进程真的在吃接近 2 核，不是"单核饱和、第二核闲着" |
| `nr_throttled` | 68 → 109（约 25 s +41，≈1.6 次/秒） | **2 核配额已成硬顶**，容器被周期性按暂停 |
| PG active | 2 ~ 12（**始终 < 连接池 17**） | 连接池没打满，不是池排队 |
| PG 行锁等待 | 累计 41，单次最多 **8 个并发在等锁** | 固定 `session_id` 造成的行锁竞争**确实存在** |
| `WALWrite` | 累计 8 | fsync 不是主矛盾 |
| PG IO 等待 | 每次 0~1 | 几乎不读盘（页缓存命中） |

派生：`每请求 CPU ≈ (171% × 1000ms) ÷ 203.5 ≈ 8.4ms`（含测量误差，只作量级参考）。

### 5.3 这一批推翻了早先的一个假设

批次① 的归因曾写作「瓶颈为 JS 主线程单核饱和」。**采样推翻了它**：

- 若是单线程饱和，CPU 应稳定在 ~100% 且 `nr_throttled` 不涨；
- 实际 CPU ≈171%、throttle 持续上涨 → **总 CPU 需求超过了 2 核配额**。

那 1.7 核大致来自：JS 主线程（~1 核）+ Prisma 引擎线程（SQL 编解码）+ V8 GC + libuv。

**本报告从此不再沿用"单核饱和"的说法。**

即使拿旧口径最好一轮去比，新口径仍然更快 —— 这条结论不依赖中位数。

### 6.5 结论

1. **行锁竞争确实拖慢接入层**，代价 ≈ **13.5% 吞吐 / 12~18% 尾部延迟**。
   与探针估算的「+20~50%」方向一致，但幅度更保守（探针那是上界估计）。
2. **损伤主要体现在尾部**：A2 的 `max` 是 B2 的 1.9 倍。行锁等待不会均匀分摊，
   而是偶发地把单个请求拖长 —— 这正是 p99 遭殃的形态。
3. **200 并发仍是负收益**：C2 吞吐 308.4 < B2 的 331.1（−6.9%），
   而 p50 从 142 ms 涨到 571 ms（**4.0×**），并**开始出现超时**（批次① 的 200 并发是 0 超时）。
   → 拐点仍在 50 以下。
4. **worker 是第二道瓶颈，但它能"事后追平"**：
   - C2 结束时：29,566 行，其中 **22,772 行未归并**，Redis 压着两万多 job；
   - 压测停止后 **≤ 6 分钟**全部追平（`processed_at IS NULL` 归零）。
   - 反推消费速率：`22,772 ÷ 约 360 s ≈ 63 events/s`，而 C2 生产速率 ≈ 310 events/s
     → **差距 4~5 倍**。准确含义是：**持续负载下积压线性增长，压力停后才收敛**，
     不是"永远追不上"。
   - 另注：29,566 条事件最终只归并成 **1 行 `error_groups`**（bench payload 的
     type/message/stack 完全相同 → 指纹相同）。也就是说每次归并都在**修改同一行** ——
     这与 §5.2 观察到的 `sessions` 单行行锁是**同一类问题**，只是发生在 worker 侧。
     ⚠️ 这条是**假设，尚未验证**；判别方法见 §10-2。

## 7. 批次④：被废弃的首次 A/B（方法论反例）

首次执行（15:40~15:45）**不可用**。原因：每组之间 `TRUNCATE` 了事件表，

## 9. 方法论沉淀（这几条比数字更值钱）

1. **每组之间必须同时清表 + 清队列 + 等几秒**。只清表会把垃圾 job 留到下一组，制造 15% 的假差异。
2. **必须 3 轮取中位数**。批次① 里有两轮单点塌方（50 并发第 3 轮、200 并发第 1 轮），只看单轮结论会完全跑偏。
3. **一次只改一个变量**。A2→B2 只改 payload 身份字段；C2 才改并发。
4. **派生指标（实测/理论、单连接效率）是"数据可信度"的体检**。实测/理论稳定在 0.85~0.95 才说明没有隐藏排队。
5. **`timeouts` 和 `non2xx` 必须逐轮看，不能只看中位数行**。C2 的中位数行 timeouts=53，但真正炸的是第 2、3 轮（53/64）。
6. **跨批次绝对值不可比**。轮次时长（20 s vs 30 s）、隔离措施、队列状态任何一项不同，绝对值就会漂。
7. **采样动作本身有成本**。批次② 的 203.5 rps 里含着 13 次 `docker exec` 的开销 —— 采样数据只用于归因，不用于出吞吐结论。
8. **判断「消费不过来」必须看压力停止之后**。压测刚结束时看到 22,772 条未归并，
   很容易直接写成"worker 追不上"；但它在 6 分钟内追平了。正确表述是
   **"持续负载下积压增长，停压后收敛"**，并给出反推的消费速率（≈63 events/s）。
   瞬态积压 ≠ 能力不足 —— 这条差点被我自己写错。
